## 概述

架构决策记录（ADR）在决策发生时记录背景约束、选择与代价，作为不可修改、可被取代的长期决策单元。

## 核心机制

- 每条 ADR 在决策当时写定，之后不修改；决策被推翻时新开一条并把旧条目标为 Superseded by ADR-xxxx，保留决策演化链条。
- Context 记录使该决策成立的前提约束；Alternatives 记录被否方案及否决原因；Consequences 记录收益、代价以及应重新评估的触发条件。
- ADR 只承载“为什么这样定”，行为契约由 spec 承载、实施步骤由 design 或任务文档承载，避免同一事实在多处维护并逐渐分叉。

## 要点

- 判定是否值得写：影响多模块或长期架构、回退成本高、未来一定会有人追问“为什么不用 X”，满足任意两条才写。
- Consequences 是 ADR 的核心：只写收益不写代价会退化成自我辩护，必须写明失效条件和重新评估的触发点。
- ADR 不是设计文档、spec、changelog 或 commit：它记录决策时刻的权衡快照，一个变更可以产生 0 到多条。
- 价值在于减少已决问题的重复争论、降低人员流动与 AI 上下文丢失造成的知识流失，并让架构演进以显式 supersede 的方式发生。
- 写 ADR 的过程本身是强制权衡机制：要求作者写清约束、被否方案与代价，能在编码前暴露拍脑袋决策，其价值往往大于文档被阅读的价值。
- 按决策可逆性分配记录成本：难回退的 one-way door 决策值得写 ADR，易回退的 two-way door 决策留在 design.md 或代码注释即可。
- ADR 的典型失效模式是形式主义与腐烂：只增不审、只写收益不写代价；需要 supersede 机制与定期回顾，否则会变成无人阅读的文档坟场。
